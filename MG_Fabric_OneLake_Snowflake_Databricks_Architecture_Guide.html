Microsoft Fabric OneLake vs. Snowflake vs. Databricks

Detailed architecture explanation and enterprise comparison

Microsoft Fabric OneLake, Snowflake, and Databricks are three major platforms in the modern enterprise data architecture landscape. However, they are fundamentally different products, and it is important to understand their architectural differences before deciding how they should coexist in an enterprise environment.

Start with the distinction
  • OneLake is primarily a unified data storage and access foundation within Microsoft Fabric.
  • Snowflake is a cloud-native data platform combining storage, compute, data management, and analytics.
  • Databricks is a data intelligence platform built around the lakehouse architecture, combining data engineering, data science, machine learning, AI, and SQL analytics.

OneLake should therefore not be viewed as a direct replacement for either Snowflake or Databricks.

How to read this comparison

Look at the platforms from two perspectives:

  1. Data architecture: How data is stored, accessed, processed, governed, and shared.
  2. Enterprise architecture: What role each platform should play, whether they should coexist, and how to avoid unnecessary data duplication, integration complexity, and vendor lock-in.

1. Understanding Microsoft Fabric and OneLake

1.1 What is Microsoft Fabric?

Microsoft Fabric is an integrated, SaaS-based analytics platform. It brings multiple data and analytics capabilities into one environment.

Fabric componentPrimary responsibility
OneLakeUnified logical data lake and storage foundation
Data FactoryData integration, ingestion and orchestration
Data EngineeringApache Spark-based data processing
Data ScienceMachine learning and data science
Data WarehouseSQL-based enterprise data warehousing
Real-Time IntelligenceStreaming and event analytics
Power BIBusiness intelligence, semantic models and reporting

The key architectural concept is that these workloads share a common storage foundation: OneLake. Instead of requiring every workload to maintain its own independent storage, Fabric allows workloads to access shared data.

1.2 What exactly is OneLake?

OneLake is Microsoft's unified logical data lake for an entire Fabric tenant. It is built on Azure Data Lake Storage Gen2 technology, but Microsoft manages the underlying storage infrastructure as part of Fabric.

Think of OneLake as an enterprise-wide logical storage layer, similar conceptually to how OneDrive provides a unified file-storage experience for Microsoft 365. However, OneLake is designed for analytical data rather than general-purpose documents.

  • Provide a common data storage foundation for Fabric workloads.
  • Reduce data duplication between analytical engines.
  • Make data easier to discover and share.
  • Support open data formats.
  • Provide centralized security and governance capabilities.
  • Enable different analytical engines to work with the same underlying data.

OneLake is automatically provisioned when an organization has a Fabric tenant. There is no need to independently provision an Azure Data Lake Storage account for the OneLake service itself.

1.3 OneLake architecture and hierarchy

Illustrative organization: workspaces contain Fabric items, and their data is stored in the tenant's OneLake.

Tenant: Represents the organization's Fabric environment and provides the organizational boundary for OneLake.

Workspace: Logical containers for organizing data and analytical assets. They can be organized by business domain, project, application, or environment.

Data items: Examples include Lakehouse, Warehouse, Mirrored database, Semantic model and Eventhouse.

1.4 How does OneLake physically store data?

OneLake supports open analytical data formats, particularly Delta Lake (based on Parquet) and Apache Iceberg.

A Delta table generally consists of:

  • Parquet files containing the actual data.
  • A transaction log containing metadata and transaction history.
  • Schema information.
  • Table version information.

Open formats create opportunities for different analytical engines to work with the same underlying data. However, open formats do not automatically guarantee complete interoperability. Catalog integration, table-format support, transaction management, security, and write compatibility must also be considered.

1.5 OneLake Shortcuts – Zero-copy data access

Important enterprise architecture capability

A shortcut is a logical reference to data stored somewhere else. It makes external data appear as though it is part of OneLake, without physically copying the data.

Conceptual illustration: shortcut creation does not itself copy the referenced files.

For example, an organization may have customer transaction data in an AWS S3 bucket. Instead of extracting and copying the data into OneLake, it can create a shortcut to supported S3 data. The actual data remains in S3.

Shortcuts primarily reference files and open-format data. A traditional SQL Server database table cannot simply be exposed as a file shortcut.

1.6 OneLake Mirroring – Replication and metadata integration

Mirroring is different from shortcuts. Fabric provides different approaches, and their data movement behavior differs.

TypeFunctionData copied?
Database mirroringReplicates database changes into OneLakeYes
Metadata mirroringSynchronizes metadata/catalog references for supported external dataNot necessarily; depends on mechanism
Open mirroringAllows supported producers to publish changes into FabricData is written into OneLake

Example: Snowflake integration

Scenario A – Snowflake data replication: Fabric connects to Snowflake, selected tables are replicated, data is stored in OneLake in Delta format, and Fabric workloads can query the replicated data. This creates a second physical copy.

Scenario B – Snowflake Iceberg tables: Where the table, storage and catalog configuration are supported, Fabric can reference underlying Iceberg data through shortcuts. The data remains in its original storage location.

Scenario C – Metadata mirroring: Fabric can synchronize external catalog metadata and reference open-format data rather than copying the underlying table data. Validate exact source support and behavior.

1.7 Direct Lake – A particularly important Power BI capability

Direct Lake allows Power BI semantic models to access supported Delta tables in OneLake directly, without requiring a conventional full import into the semantic model or issuing a DirectQuery for every report interaction.

ModeBehavior
ImportData is loaded into the Power BI semantic model.
DirectQueryPower BI sends queries to the underlying data source.
Direct LakePower BI accesses supported OneLake Delta data directly.

Direct Lake is not a universal connector to all external databases. If data is in a proprietary Snowflake table, Direct Lake cannot simply read it as a native OneLake Delta table. Use the Snowflake connector, an appropriate replication path, or supported open-format interoperability.

2. Understanding Snowflake architecture

Snowflake is a cloud-native data platform designed primarily for data warehousing, SQL analytics, data engineering, and increasingly AI workloads.

Its architecture has three main layers.

2.1 Storage layer

Snowflake stores data in cloud object storage managed as part of the Snowflake service. The underlying cloud provider can be AWS, Microsoft Azure or Google Cloud Platform.

Snowflake manages the physical storage infrastructure. Traditional native tables use Snowflake-managed storage structures, including micro-partitions. Snowflake also supports Apache Iceberg tables, enabling interoperability with external engines.

2.2 Compute layer

Snowflake uses virtual warehouses for processing SQL queries and other workloads. A virtual warehouse is an independent compute cluster.

Virtual warehousePurpose
WH_FINANCEFinance reporting
WH_SALESSales analytics
WH_ETLData transformation
WH_DATA_SCIENCEData science workloads

One of Snowflake's major advantages is workload isolation. Different virtual warehouses can process queries against the same underlying data without necessarily affecting each other's compute resources. Compute can be independently scaled.

2.3 Cloud services layer

This layer manages authentication and authorization, query parsing and optimization, metadata management, access control, security and infrastructure coordination.

2.4 Snowflake's architectural strengths

  • Enterprise SQL data warehousing.
  • Independent compute scaling.
  • Workload isolation.
  • Structured and semi-structured data analytics.
  • Data sharing between organizations.
  • Managed data platform operations.
  • SQL-centric analytics and data engineering.

Snowflake is no longer just a traditional data warehouse. Its support for Iceberg, Python, Snowpark, and AI workloads has expanded its capabilities significantly.

3. Understanding Databricks architecture

Databricks is built around the Lakehouse architecture. The fundamental idea is to combine the advantages of data lakes (scalability, flexibility and low-cost object storage) with data warehouses (structured data management, reliability, transactional consistency and SQL analytics).

Unlike Fabric, Databricks is designed to work with the cloud provider's object storage.

3.1 Storage layer

Databricks uses open data formats. Its primary table format is Delta Lake, which provides ACID transactions, schema enforcement, schema evolution and time travel. Databricks also supports Apache Iceberg. The data is stored in the organization's cloud storage rather than exclusively in a proprietary Databricks storage environment.

3.3 Governance layer – Unity Catalog

Unity Catalog is Databricks' centralized data and AI governance solution. It provides data discovery, access control, data lineage, auditing, metadata management, classification and governance across supported workspaces and environments.

3.4 Databricks' architectural strengths

  • Large-scale data engineering.
  • Complex ETL and ELT processing.
  • Advanced analytics.
  • Data science and machine learning.
  • Generative AI and AI development.
  • Batch and streaming processing.
  • Open data architecture.
  • Multi-cloud data processing.

Databricks is particularly attractive when an organization has sophisticated data engineering, machine learning, and AI requirements.

5. How the three platforms can work together

Rather than choosing one platform to replace everything, an enterprise can use the three platforms for different responsibilities.

5.1 Scenario A – Snowflake is the primary data warehouse

  1. Snowflake remains the system of record for curated analytical data.
  2. Power BI connects to Snowflake through its supported connector.
  3. Depending on requirements, Power BI uses Import or DirectQuery.
  4. OneLake is not required to store a second copy of Snowflake data.

Advantages: Preserves existing Snowflake investment, avoids mandatory migration, minimizes unnecessary duplication, and allows Fabric to be adopted primarily for Power BI.

5.2 Scenario B – Fabric becomes the enterprise analytics platform

OneLake becomes the shared logical data foundation. Fabric provides integration and transformation capabilities; Power BI consumes curated data through Direct Lake where supported; Snowflake and Databricks remain operational platforms for specialized workloads.

This does not mean every source should be migrated into OneLake.

5.3 Scenario C – Databricks is the enterprise lakehouse

Databricks is the primary data engineering and data science platform. Data resides in ADLS or S3; Delta Lake and Iceberg provide open table formats; Unity Catalog provides governance. Snowflake can coexist for specialized SQL warehousing. Power BI connects to Databricks SQL or other supported interfaces.

6. OneLake and cross-cloud data access

OneLake is particularly interesting for enterprises with data distributed across multiple cloud providers.

There are several integration patterns:

PatternData movementWhen to use
Direct connectivityNo initial copyQuery external databases directly
OneLake shortcutsNo initial copyAccess supported external open-format files/tables
MirroringUsually yes for database replication; varies by mechanismContinuously replicate databases or reference external catalogs
ETL/ELT pipelinesYesTransform, consolidate or move data
Important architectural warning

Zero-copy does not mean zero cost or zero latency. For cross-cloud access, consider network latency, AWS data egress charges, Azure network charges, source system query consumption, concurrent query workloads, caching, data transfer volume and network security.

It is often better to keep compute close to the data for heavy processing and use cross-cloud access for appropriate analytical consumption.

7.2 Recommended architectural principles

  1. Source data ownership remains with the source platform. Snowflake, Databricks, ADLS, S3 and on-premises databases retain ownership of their data. Fabric should not automatically become another enterprise data repository.
  2. Prefer direct connectivity or zero-copy access. Use native connectors, shortcuts and metadata mirroring where technically appropriate.
  3. Use replication only when justified. Legitimate reasons include performance, Power BI Direct Lake, source workload isolation, data consolidation, cross-system analytics, and regulatory or operational requirements.
  4. Separate data engineering from BI consumption. If Databricks or Snowflake already performs enterprise data engineering, avoid unnecessarily rebuilding the same ETL processes in Fabric.
  5. Establish enterprise-wide governance. Define consistent data ownership, identity, security, lineage, data classification and access management across all platforms.

7.3 Important limitations and considerations

OneLake shortcuts are not universal database connectors

A shortcut to AWS S3 is not equivalent to a shortcut to an AWS-hosted Snowflake database. The former references supported storage objects. The latter requires a database integration mechanism.

Fabric mirroring has source-specific limitations

Feature support, source versions, authentication, network connectivity, table limits and regional availability can vary. For example, Snowflake mirroring documentation has specified limitations around table counts, workspace identity authentication and private connectivity. These details are subject to change and must be checked against current documentation before design approval.

Security must be designed across platforms

Microsoft Entra ID, Snowflake authorization, Databricks Unity Catalog and AWS IAM/S3 policies are distinct security systems. Permissions should not be assumed to propagate automatically.

Direct Lake does not eliminate every data movement requirement

Direct Lake requires supported OneLake data structures. For proprietary external tables, compare direct Power BI connectivity, replication into OneLake, and open-format sharing using Delta or Iceberg.

Central recommendation

Microsoft Fabric Power BI should be the enterprise BI and reporting platform without automatically requiring the enterprise to migrate or duplicate its existing data into OneLake.

Define whether OneLake is an integration/access layer for existing data platforms, a destination for selected curated analytical data, or both under explicit rules. This avoids creating three competing enterprise data repositories and duplicating data engineering capabilities.

8. Discussion checklist and references

8.1 Discussion questions for the architecture review

  1. What is the target role of Fabric: BI-only, integrated analytics, or strategic enterprise data platform?
  2. Which platform is authoritative for each major data domain and curated data product?
  3. What datasets genuinely require OneLake persistence, and which should remain external?
  4. Which Direct Lake use cases justify replicating data into OneLake?
  5. Which cross-cloud access paths are acceptable from a latency, security and cost perspective?
  6. What is the standard pattern for on-premises connectivity and gateway high availability?
  7. How will enterprise metrics and semantic models be governed across Power BI, Snowflake and Databricks?
  8. What operational model will monitor cost, performance, freshness, lineage and incidents across platforms?

8.3 Important qualification

This guide is intended as a discussion aid and conceptual architecture comparison. It is not a product support matrix, security design, performance benchmark, licensing assessment or implementation specification. Product capabilities change; verify the exact source version, cloud, region, SKU, identity configuration, network path and feature status for each proposed integration.

Closing architecture principle

Use each platform where it provides clear enterprise value. Preserve source ownership, avoid default data duplication, choose integration patterns by workload, and make cross-platform security and operations explicit.
